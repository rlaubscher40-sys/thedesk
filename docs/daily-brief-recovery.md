# Daily brief delivery recovery

The daily email used to run inside the ingestion request's detached callback. A restart could lose delivery, and AI retry delays could let the callback send before the selected stories were finished. Subscriber sent dates were updated only after the whole send loop, leaving an ambiguous retry window after provider acceptance.

Daily ingestion now only persists stories and wakes AI processing. A separate worker starts after database migrations and polls every minute. It sends only on Sydney weekdays from 07:00 inclusive to noon exclusive, using Australia/Sydney timezone rules through daylight saving. It reads only that Sydney day's stories and never sends an old brief automatically. It requires a configured email provider and does not send in demo mode.

Before preparing a brief, it reads the five highest-priority Australian/property stories together with their durable AI completion markers in one database snapshot. All selected stories must be completed, including valid editorial all-null results. A missing, pending, failed or skipped marker holds delivery for review. Empty feed days remain unsent. The first ready selection is saved in `daily_brief_batches`; subsequent polls and replicas use that same selection.

Each confirmed subscriber has one `daily_brief_deliveries` record per date. Claiming the record also freezes the rendered message, recipient, sender, unsubscribe headers and links. A unique owner and two-minute database-clock lease fence stale workers. Provider calls retain the existing ten-second timeout and 600ms pacing. At most 50 candidate recipients are examined per poll, and overlapping local polls share one runner. Three attempts are allowed, with five-minute delays after unsuccessful provider calls. A crash consumes an attempt; an expired final claim becomes failed. No provider call occurs under a database transaction.

Automatic requests use `Idempotency-Key: daily-brief/v1/<date>/<subscriber-id>`. Resend documents 24-hour idempotency retention and requires an identical payload for retries: [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys). Freezing the rendered request keeps the payload unchanged across template edits, sender configuration changes and redeploys. The same-day five-hour delivery window stays within that retention period. An ambiguous timeout is retried with the same key and message, never a new key. This protection is specific to the documented provider contract, not a guarantee of inbox placement.

Immediately before sending, the worker rechecks ownership, the morning window, confirmed status, unsubscribe status, recipient address and any prior recorded brief delivery. A changed/ineligible subscriber is skipped. Consent changes after that final check or a request already accepted by the provider cannot retroactively cancel the send. An explicit Admin resend is still a deliberate resend and is not part of the automatic retry guarantee.

Provider acceptance and the subscriber's last sent date commit together. Sent dates never move backwards. The message payload is cleared on accepted, skipped, failed or expired status. Noon and next-day cleanup expire unfinished sends; they are never revived the next morning. Admin shows today's preparation and delivery counts, plus recent failed/expired subscriber IDs without exposing addresses or message bodies. A missing provider key does not consume attempts.

Validation uses mocked provider calls, Sydney winter/summer boundaries, readiness failures, unsubscribe changes, immutable retry content, concurrent MySQL claims, expired-owner rejection, receipt persistence and bounded retries. No test messages or artificial stories are sent to production subscribers.
