# Daily story enrichment recovery

Daily-feed ingestion used to commit a story and then launch untracked work in `setImmediate`. A restart could lose the work while the duplicate guard prevented the same URL from being inserted again. A failure in one concurrent runner could also abandon the remaining batch.

New AU and PROPERTY stories now insert a `feed_enrichment_jobs` row in the same transaction as the feed row and URL claim. Failure to persist the job rolls back the story too. BUSINESS, TECH and GLOBAL remain coverage-only. Existing feed history is not automatically queued or charged for a backfill. The job stores only the first 6,000 trimmed article characters, exactly the article excerpt used by the existing prompt, plus its title, summary and category. This input is removed on completion, skipping or terminal failure.

A worker starts after startup migrations and polls once per minute, independently of the scheduler flag. Successful ingestion also wakes it immediately. Each pass handles at most 40 jobs, with four concurrent calls per process. Database row locks serialise claims across processes. Five-minute leases use the database clock; a unique owner token fences writes from abandoned workers. A two-minute abort deadline and zero SDK retries apply to each queued model call. The queue allows three attempts, waiting one minute after the first failure and five minutes after the second. A crash consumes an attempt; an abandoned final attempt becomes failed when its lease expires.

The response fields and completion marker commit in one transaction. Only previously null fields which are still null are filled, preserving source presets, existing generated values and concurrent manual text or empty-string edits. Changing a story's title, summary, category or switching it to a coverage lane causes stale output to be skipped. Deleted stories are skipped. Valid all-null results are completed, because an editorial decision to omit an angle is not a transport failure. Missing fields, malformed JSON and provider errors trigger the retry budget. Fully populated stories need no model call. The public feed cache is invalidated after a successful save.

Admin's **Story AI recovery** card shows pending, running, completed, skipped and failed job totals and the ten most recent failed item IDs. Counts cover jobs created after this release, not all historical stories. Terminal failures need editorial review before the existing manual generation controls are used; there is no automatic infinite retry or bulk replay button. Demo mode does not run the database worker.

The queue does not promise exactly-once provider billing: a process can die after the provider returns but before the result commits. That unsaved result may require another call, within the three-attempt limit. Once the result and completion marker commit, normal recovery never regenerates it. Individual leases prevent two healthy workers from processing the same job; after a long process pause, a stale provider request could overlap recovery, but its database writes are fenced.

Daily story angles and weekday brief delivery now have separate recovery workers. See [daily brief delivery](daily-brief-recovery.md) for the morning window, immutable email snapshots and recipient-level retry protection. Weekly edition generation retains its existing best-effort behaviour. Terminal job metadata is retained for review; the article excerpt is cleared. No production failure injection or historical paid backfill is required for verification.

Verification includes real MySQL races, restart-style reclamation, expired-owner rejection before and after takeover, atomic completion, preset/manual preservation, deleted/changed stories, intentional null completion, bounded retries, exhausted crash attempts and independent progress after a story fails. Prompt tests distinguish invalid responses from valid editorial omissions and check the cancellation/retry options without calling a live model.
